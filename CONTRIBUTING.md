# Contributing to GitCat

For install/build/test commands, see the [Development](README.md#development) section of the README. This file is about getting *oriented* in the codebase before you start reading or changing it.

## Look at the history before the code

Before diving into any unfamiliar codebase, a few `git log` queries tell you more than the first hour of reading source ever will — which files are the real center of gravity, and whether that's by design or by accident. (Inspired by [this post](https://piechowski.io/post/git-commands-before-reading-code/); worth reading in full.)

Most-changed files in the last year:

```bash
git log --format=format: --name-only --since="1 year ago" | sort | uniq -c | sort -nr | head -15
```

Run today, that's:

```
61  index.html
45  src/legacy/main.ts
42  src-tauri/src/lib.rs
38  src/ipc/bindings.ts
34  src/main.ts
25  src/islands/sidebar/Sidebar.svelte
20  src/islands/sidebar/sidebar.svelte.ts
18  src-tauri/src/menu.rs
```

**That's expected, not a red flag** — each one is a real architectural hub, not an accumulation of patches-on-patches:

- **`index.html`** / **`src/legacy/main.ts`** — the original single-file vanilla app: the canvas commit-graph renderer, drag-and-drop, and (in `index.html`) every shared CSS class the Svelte islands themselves reuse. Almost any new UI feature touches one or both, by design (see `src/legacy/bridge.ts`'s own doc comment for how islands reach into this layer).
- **`src-tauri/src/lib.rs`** — the single `collect_commands!` list every Tauri command is registered in. Every new backend command, however small, adds one line here.
- **`src/ipc/bindings.ts`** — auto-generated (see below); churns on every backend change by design, never by hand.
- **`src-tauri/src/menu.rs`** — the native app menu; every Tools-menu/⌘K-reachable feature adds a menu item and an id here.

If you're about to touch one of these files and it looks unfamiliar or sprawling, that's normal for this codebase's shape — read the surrounding doc comments (this repo leans heavily on inline "why" comments over separate design docs) before assuming it needs a refactor.

This project is also very young — every commit so far is from July 2026 — so "history" here means days, not years. The technique still holds; there's just less of it yet.

## Where things live

- `src-tauri/src/` — Rust core. `git2` for reads, the `git` CLI for writes (every mutation snapshots first via the Safety Manager). One file per feature area (`git_bisect.rs`, `submodule.rs`, `tool_settings.rs`, …), each with its own module-doc comment explaining its own design decisions.
- `src/islands/<name>/` — one Svelte 5 "island" per feature (a `.svelte.ts` runes controller + its `.svelte` view, some with no view at all — see `applypatch.svelte.ts`/`forcepush.svelte.ts` for the "no modal, just fires a command" shape).
- `src/legacy/` — the original vanilla-canvas app (`main.ts`, `@ts-nocheck`) and `bridge.ts`, the live-binding seam islands use to reach into it.
- `src/ipc/bindings.ts` — auto-generated by tauri-specta; never hand-edit, regenerate with `cd src-tauri && cargo test export_bindings`.
- `docs/` — the [VitePress](https://vitepress.dev) marketing/docs site, deployed separately from this file. The homepage's section stack is `docs/.vitepress/theme/Landing.vue`, not `index.md` (which carries only the hero).

## Docs site assets

- **Screenshots** — `pnpm screenshots` regenerates every PNG in `docs/public/screenshots/` by driving the app's browser demo mode through Playwright. It's deterministic, so rerun it when the UI shifts rather than cropping a one-off manual capture.
- **Tama's portraits** — the site serves them from `docs/public/tama/`, which is a *copy* of `design/assets/optimized/`. VitePress only publishes what's under `docs/public/`, so a symlink wouldn't survive the Pages build. If you regenerate the art, copy it across or the site quietly keeps showing the old faces.
- **The homepage demo video** — recorded by hand against a real repository (the current one is a ~56s CPython session). A headless capture was tried twice and dropped: it has no native window chrome and no real cursor, and both show. Record at 1440p or better with the window at a normal size, keep it silent and under about a minute, then run:

  ```bash
  scripts/encode-demo.sh ~/path/to/recording.mov 00:00:12
  ```

  That produces the `demo.webm` / `demo.mp4` / `demo-poster.jpg` trio in `docs/public/` with the settings the homepage embed expects (1080p30, no audio, faststart). The second argument is the timestamp to pull the poster still from.

## Contributing translations (i18n)

The UI is translatable. **English is the source of truth**, and everything falls back to it gracefully: `t()` resolves a key as `current locale -> English -> the key itself`, so a missing translation just shows the English text, never a blank or a crash. **You do not need to speak a language to contribute to it, and you are never blocked for leaving one incomplete** — there is deliberately no CI check that requires the locales to be in sync.

Strings live in `src/i18n/locales/<locale>/<namespace>.ts`, one flat file per feature area:

```ts
// src/i18n/locales/en/sidebar.ts   (the filename is the namespace)
export default {
  hide_all: "Hide all branches",
  push_failed: "Push failed — {error}",   // {name} placeholders are filled by t("sidebar.push_failed", { error })
};
```

- **Fix or improve a translation** — edit the string in `src/i18n/locales/<locale>/<namespace>.ts` and open a PR. That's the whole change.
- **Fill in a missing string** — find the key in the `en/` file, add the same key with your translation to the matching `<locale>/` file. Partial is fine; whatever you don't add stays English.
- **Add a new language** — it's purely additive:
  1. Add the id + label to `Locale` and `LOCALES` in `src/i18n/i18n.svelte.ts`.
  2. Create `src/i18n/locales/<locale>/` and translate the namespaces you can (copy the `en/` files and translate their values; the loader picks the folder up automatically — no other wiring).
  3. If the script needs it, add font fallbacks to `--ui` / `--display` / `--mono` in `index.html` (the rounded display font has no CJK, for example).

Backend messages work the same way: app-authored Rust errors are returned as `i18n:<namespace>.<key>` (see `src-tauri/src/i18n_err.rs`) and translated on the frontend, so their strings live in these same locale files. Raw `git` output is passed through untouched and is not translated.

Before opening the PR, run `pnpm test` and `pnpm check`. `pnpm test` matters specifically here: the locale files are loaded at runtime by a Vite glob, so only actually running the app/tests (not just a type-check or build) proves your files load.
